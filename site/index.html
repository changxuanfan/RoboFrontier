RoboFrontier

Benchmarking How LLM Agents Organize, Communicate, and Collaborate in a Multi-Robot World

Can language models run a robot world? RoboFrontier puts language-model agents in charge of up to sixteen robot arms in Robo World, a physical simulation. They read the task, split the work, talk and recover from mistakes, and are measured on all of it.

01 · Overview

An agent, a robot tool and a world that pushes back.

Every model drives the same arms through the same tool, sees the same cameras and obeys the same rules. Nothing is scripted: allocation, timing, communication and recovery are the agent's choices.

A

Language agents

Native Codex and Claude Code sessions. One Controller owns the task; in adaptive mode it spawns delegates for bounded jobs and takes their arms back.

tool calls →
B

One robot tool

Move arms and grippers, batch and pre-check motions, observe from named cameras, wait for events, message teammates, delegate and hand work back. Every call is logged with its outcome.

← images · events
C

Robo World

Robo World runs MuJoCo dynamics with real contacts and simulated Franka Panda arms: grasps slip, timbers swing, springs push back. No teleporting, no state writes, no resets.

Same contract

Identical tasks, physics, tools, prompts and limits for every model.

Long horizon

Each run gets 24 hours of wall time from its START. Planning and waiting count.

Outcome first

Success is judged on the final world state; collisions, retries and process events are reported beside it.

Fully recorded

Every action, message, camera image and motion frame is kept; motion can be replayed and re-rendered.

02 · Benchmark

Four ways to work together.

Each family has nine tasks: three team sizes crossed with three difficulty levels. Hover a family to watch an Oracle reference run.

The task matrix

Columns scale up the team, rows raise the difficulty. Select any cell to play its Oracle reference run.

Protocol

The Controller decides who works.

All benchmark runs use the adaptive protocol. A single Controller reads the task, keeps the plan and either drives arms itself or delegates a bounded job — "stack row 3 with arms C and D" — to a forked delegate, which hands the arms back when its job is done.

  • Delegates are forks of the Controller's own session: they inherit what it knows.
  • Arms have exactly one owner at a time; ownership moves with delegation and return.
  • Messages go through the robot tool, so every exchange is part of the record.

04 · Results

Who gets the job done?

Every model runs the adaptive protocol on all 36 tasks, for up to 24 hours each. Completion is the headline; how they got there is the story.

How each metric is defined
Completion rate
Share of runs whose final world state meets the task's completion conditions, judged by the independent scorer.
Mean progress
Share of the task's goals met at the end: targets, cells or timbers placed; for Dial, an unlock counts as complete.
Failed actions, failure rate
Robot actions that ended in failure (for example a grasp outside tolerance or a timeout), per run and as a share of all actions.
Retries, retry rate
Actions that repeat the same operation on the same arm right after that arm's failed action.
Time to finish
Wall time from START to completion, over completed runs only.
Input, output tokens
Provider-reported tokens over every session of a run: Controller and all delegates.
Arm collisions
Contact episodes between two different robots.
Parallel efficiency
Mean number of moving arms divided by the number of arms, while any arm is moving. An arm moves when a joint turns faster than 0.02 rad/s.
Messages
Messages sent between roles through the robot tool.

05 · Analysis

What makes a team work?

Three questions behind the leaderboard: how agents should communicate, whether written skills help, and how much work really happens in parallel.

The benchmark uses Adaptive. This study compares it with three fixed organizations: the same GPT model on the four largest Level 3 tasks, one per family.

Agents may write lessons into a shared skills.md during a run. We compare runs with and without that skill file: progress over time, and how often they repeat failed attempts late in the run.

How many arms actually move at once? Parallel efficiency is the mean number of moving arms divided by the number of arms, measured while any arm is moving.
