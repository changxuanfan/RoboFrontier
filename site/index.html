RoboFrontier

Can Multimodal Agents Work Together on Long Physical Tasks?

Can multimodal agents run a robot world? RoboFrontier puts multimodal agents in charge of up to sixteen robot arms in Robo World, a physical simulation. They read the task, split the work, talk and recover from mistakes, and are measured on all of it.

01 · Overview

An agent, a robot tool and a world that pushes back.

Every model drives the same arms through the same tool, sees the same cameras and obeys the same rules. Nothing is scripted: allocation, timing, communication and recovery are the agent's choices.

A

Multimodal agents

Native Codex and Claude Code sessions. One Controller owns the task; in adaptive mode it spawns delegates for bounded jobs and takes their arms back.

tool calls →
B

One robot tool

Move arms and grippers, batch and pre-check motions, observe from named cameras, wait for events, message teammates, delegate and hand work back. Every call is logged with its outcome.

← images · events
C

Robo World

Robo World runs MuJoCo dynamics with real contacts and simulated Franka Panda arms: grasps slip, timbers swing, springs push back. No teleporting, no state writes, no resets.

Same contract

Identical tasks, physics, tools, prompts and limits for every model.

Long horizon

Each run gets 24 hours of active time from its START. Planning and waiting count; pauses for outages or usage limits do not.

Outcome first

Success is judged on the final world state; collisions, retries and process events are reported beside it.

Fully recorded

Every action, message, camera image and motion frame is kept; motion can be replayed and re-rendered.

02 · Benchmark

Four ways to work together.

Each family has nine tasks: three team sizes crossed with three difficulty levels. A larger team brings more arms and more work; a higher level changes the physics of the job itself.

What changes from task to task

Pick a family. Columns add arms and work; rows raise the level. Each image is the task's real initial state; hover to watch its Oracle run, select to open it.

All 36 tasks share one floor.

Robo World as a map: the four zones in their floor colors, nine tables each. A table grows with its team; every dot is an arm.

Protocol

The Controller decides who works.

All benchmark runs use the adaptive protocol. A single Controller reads the task, keeps the plan and either drives arms itself or delegates a bounded job — "stack row 3 with arms C and D" — to a forked delegate, which hands the arms back when its job is done.

  • Delegates are forks of the Controller's own session: they inherit what it knows.
  • Arms have exactly one owner at a time; ownership moves with delegation and return.
  • Messages go through the robot tool, so every exchange is part of the record.

03 · Videos

Every task, on film.

Every run rendered in Robo World, front and side. Model runs appear here as they are rendered; the Oracle reference runs show that each task can be done.

Oracle runs are privileged reference programs that read hidden task state; they are not model results. Some were operator-assisted, and some predate the released physics revision; each video says which. Videos are edited for viewing: idle time removed, played at 10–30×.

04 · Results

Who gets the job done, and at what cost?

Every model runs the adaptive protocol on all 36 tasks, for up to 24 hours each. Completion alone saturates for strong models, so the board leads with how often they fail along the way; completion, time and tokens sit beside it.

How each metric is defined
Completion rate
Share of runs whose final world state meets the task's completion conditions, judged by the independent scorer.
Mean progress
Share of the task's goals met at the end: targets, cells or timbers placed; for Dial, an unlock counts as complete.
Failed actions, failure rate
Robot actions that ended in failure (for example a grasp outside tolerance or a timeout), per run and as a share of all actions.
Retries, retry rate
Actions that repeat the same operation on the same arm right after that arm's failed action.
Time to finish
Wall time from START to completion, over completed runs only.
Input, output tokens
Provider-reported tokens over every session of a run: Controller and all delegates.
Arm collisions
Contact episodes between two different robots.
Parallel efficiency
Mean number of moving arms divided by the number of arms, while any arm is moving. An arm moves when a joint turns faster than 0.02 rad/s.
Messages
Messages sent between roles through the robot tool.

05 · Studies

What makes a team work?

Three controlled comparisons beside the benchmark: whether written skills help a team improve itself, how agents should communicate, and what each arm needs to see.

Self-improvement

With and without skills

Agents may write lessons into a shared skills.md during a run. Paired runs with and without it: progress over time and late-run repeated failures.

Communication

Four ways to organize

The same GPT model on the four largest Level 3 tasks under each organization; the benchmark uses Adaptive.

Perception

Own cameras or every camera

Every arm has front and side cameras, and the hall has global views. Ego-centric runs let each role read only its own arms' cameras; the full setting opens every camera to every role.
