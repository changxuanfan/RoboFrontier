# Cleanup log, 2026-11-10

This page records what the 2026-11-10 cleanup removed from the repository, why,
and how to get it back. Nothing listed here is lost: every file is in Git at the
tag `archive/pre-cleanup-20261110` (commit `616cb709`, the `main` the cleanup
started from).

Restore one path:

```sh
git checkout archive/pre-cleanup-20261110 -- PATH
```

Earlier removals (the 2026-11-03 prune) are indexed in
[`benchmark/pruned-paths.json`](../benchmark/pruned-paths.json) with their own tag.

The cleanup runs as a series of pull requests. Each one adds a section below.

## Before the pull requests: local data

Not in Git, so listed only in summary. Old worktrees, per-run source copies and
duplicate checkouts were removed, leaving one checkout on `main`. Local test and
smoke runs were deleted. Formal runs were deleted only where a backup already
held them. Unmerged branches were kept as local `archive/branch/*` tags.

## Step 2: historical Oracle package checks

These checks re-verified the 2026-10 Dial, Mosaic and Transport Oracle packages
against today's code: they fingerprinted `robot_control.py`, `sim.py`,
`motion_check.py`, `task_config.py` and `pipeline.py` and allowed only reviewed
changes (`benchmark/source-compatibility.json`). The release is frozen and no
longer rebuilt, and these pins blocked every later cleanup of those five files.
Nothing at run time used them. They were planned for the release step and were
moved forward for that reason.

## Step 3: task types from before the released suite

Before the four released families, the runtime also ran a generated three-arm cube
task (the default when no task was given), a generated four-arm Mosaic grid
(`shared_grid`), single spring-dial and floating-dial puzzles, and a two-robot beam
handover. A run now always loads a released task (`kind: frontier_suite`); without
`--task`, `prepare_run` and the tests use the policy task of `transport-a04-d1`.

| Removed | What it was |
| --- | --- |
| `configs/tasks/` (63 files) | The generated task files and cube-transport order seeds |
| `robofrontier/beam_handoff.py`, `beam_task.py`, `spring_dial.py`, `spring_dial_task.py`, `floating_dial_task.py`, `spring_crank_task.py`, `cube_transport_presentation.py` | Those task types' builders, samplers and evaluators |
| The generated scene (`build_world`) and the `spring_dial`, `beam_handoff` and `shared_grid` branches in `pipeline.py`, `task_config.py` and `run_setup.py`; `validate_scene_task`, `sample_shared` and `evaluate_shared` in `scene_task.py` | Runtime support for those task types |
| `Simulation` in `sim.py`, `build_scene` in `scene.py` | The demo's leftovers (see PR 1) |
| `scripts/generate_cube_transport.py`, `build_mosaic.py`, `build_floating_spring_dial.py`, `verify_transport_objects.py` | Generators and checks for those task types |
| 7 test files; the generated-scene cases of `test_mosaic`, `test_cube_transport` and `test_robot_actions` | Tests of the above |

Kept until the release step: `robofrontier/cube_transport.py` and `robofrontier/mosaic.py`,
because the scene rebuild chain (`suite/scenes.py`, `suite/v2.py`) still imports them.

`test_grasp_force`, `test_hand_position_profile`) used the generated scene. They now
use `tests/single_arm_scene.py`, which writes the same single-arm geometry as a
scene folder that `World` loads like a released scene; all 24 cases pass unchanged.
Protocol tests that assumed three robots now use the default case's four.
