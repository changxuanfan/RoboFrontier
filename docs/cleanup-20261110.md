# Cleanup log, 2026-11-10

This page records what the 2026-11-10 cleanup removed from the repository, why,
and how to get it back. Nothing listed here is lost: every file is in Git at the
tag `archive/pre-cleanup-20261110` (commit `616cb709`, the `main` the cleanup
started from).

Restore one path:

```sh
git checkout archive/pre-cleanup-20261110 -- PATH
```

Earlier removals (the 2026-11-03 prune) are indexed in
[`benchmark/pruned-paths.json`](../benchmark/pruned-paths.json) with their own tag.

The cleanup runs as a series of pull requests. Each one adds a section below.

## Before the pull requests: local data

Not in Git, so listed only in summary. Old worktrees, per-run source copies and
duplicate checkouts were removed, leaving one checkout on `main`. Local test and
smoke runs were deleted. Formal runs were deleted only where a backup already
held them. Unmerged branches were kept as local `archive/branch/*` tags.

task (the default when no task was given), a generated four-arm Mosaic grid

handover. A run now always loads a released task (`kind: frontier_suite`); without
`--task`, `prepare_run` and the tests use the policy task of `transport-a04-d1`.

## Step 4: package layout

The 76 top-level modules and the `suite/`, `claude/`, `codex/` and `run_analysis/`
packages were reorganized into subpackages by what they do: `runtime/`, `physics/`,
`tasks/`, `engines/` (`claude/`, `codex/`, `common/`), `batch/`, `oracle/`, `media/`,
`analysis/` and `factory/` (with `factory/blender/`). Scripts that the package
already imported moved into it as well. Nothing was merged or rewritten: each file
kept its code, and only imports, paths and module names in commands changed. Files
that later steps merge sit next to their merge target under their own name; the
scene rebuild chain that the release step deletes stays in `robofrontier/suite/`,
with `cube_transport.py` and `mosaic.py`.

Commands change with the module path, for example `python -m scripts.tasks` is now
`python -m robofrontier.batch.tasks`. The control-code fingerprint keeps its keys,
so identical code still gives the same fingerprint. Records under `benchmark/`
keep the old paths they were made with; `benchmark/pruned-paths.json` maps the ones
they name.

`robofrontier/io.py` holds the one copy of the repository root, the file SHA-256
helper and the atomic JSON writer; eleven modules that had their own copy now import
it under their old local name. Writers with different behavior (no fsync, other
permissions) and code that runs outside the package (Oracle re-exec entries,
Blender, the Landlock wrapper) keep their own.

Tests follow the package: `tests/runtime/`, `physics/`, `tasks/`, `engines/` (with the
Node host tests), `batch/`, `oracle/`, `media/`, `analysis/`, `factory/` and `repo/`
(repository and script checks). Shared helpers and `fixtures/` stay at the top. Run a
module by its dotted name, for example
`PYTHONPATH=tests:scripts .venv/bin/python -m unittest runtime.test_pipeline`.

## Step 5: release physics and real Franka limits

This is the first step that changes behavior. New runs are not comparable with runs
made before it.

**Physics in the scenes.** `scripts/build_release.py physics` wrote the solver options and
the contact parameters into every released `scene.xml`: elliptic friction cones,
impratio 1, noslip 1e-9 with 10 iterations, one contact stiffness for every collision geom
(solref 0.004 1, solimp 0.95 0.99 0.001 0.5 2), sliding friction 0.8 for finger pads and
0.4 for every other surface, and the hand actuator's range of 280 N. The compiled models
are identical to the earlier scenes with these values applied in memory, array for
array, and a fixed-control rollout gives the same trajectory. `physics/profile.py`, which
used to change contacts at run time under the names `realtime-v1` and `realtime-v2`, now
holds only what a scene file cannot: when objects may sleep and Relay's 30 s settle.
Each run writes `private/outputs/effective-physics.json`, the physics it ran with and
its hash. A full contact or constraint buffer and a bad inertia now fail the step.

| Removed | Replaced by |
| --- | --- |
| `physics_profile` in the policy harness; profiles `realtime-v1`, `realtime-v2` and "none"; `unify_contacts` | The values in each `scene.xml`; `physics/profile.py` step settings |
| `oracle prepare --physics-profile` | The Oracle runs on its own copy of each case (below) |
| Per-call settle counting | One settle sample per simulation tick, as `realtime-v2` already did |
| The `legacy` hand servo and `gripper_position_servo` | The `pd1000-v1` hand servo, always |
| `ACTION_DEFAULTS`, `allowed_*` and `default_*` speed and force settings in the harness | `physics/franka_limits.py` |
| `tests/physics/test_rolling_physics_candidate.py`, `tests/tasks/test_relay_scene.py` | Release physics checks in `tests/physics/test_physics_profile.py`; the rebuild chain they tested no longer reproduces the release |

**Real Franka limits, no defaults.** Every move states `speed_m_s`, `acceleration_m_s2`,
`angular_speed_rad_s` and `angular_acceleration_rad_s2`; every joint move states
`joint_speed_rad_s` and `joint_acceleration_rad_s2` (one number or seven); every hand
action states `speed_m_s`, and a grasp `force_n`. The limits are the Panda's (sources in
`physics/franka_limits.py`): TCP 2.0 m/s and 13 m/s², hand rotation 2.5 rad/s and
25 rad/s², joints 2.175 or 2.61 rad/s and 7.5 to 20 rad/s², hand 0.1 m/s and 140 N per finger.
`force_n` now means the force of each finger, as in libfranka, where it was the total of
both. The controller follows straight TCP and turn references with trapezoid speed profiles
and keeps every joint within its own limits; the earlier one, whatever speed was asked,
moved the TCP at about 0.058 m/s at most.

**The Oracle's copy of the earlier release.** The Oracle and its recorded regression states
were made with the scenes before this step. Each case's earlier folder is kept as
`benchmark/oracle/<case>/` (asset files hard-linked from the released case by
`setup-assets`), `oracle prepare` runs there, and `benchmark/legacy-paths.json` points the
earlier case names at those folders. The Oracle states the speeds it was written for
(`oracle/trial.py`) and halves its forces to the per-finger meaning.

## Step 6: physics validation and scenes that start at rest

`scripts/validate_physics.py` checks the release physics and the Franka limits in the
policy runtime's own world and controller: every case at rest for 60 s, a grasped object
through fast joint turns and Cartesian moves at up to 2 m/s, a cube picked up, set down
and released, a cube pushed along the table, two arms driven into each other at full speed,
an airborne Relay handover, a Dial knob turned, and the step time of the largest case of each
family. `tests/physics/test_validation.py` runs a fast part of it. The first full run is
kept in `outputs/review/cleanup-20261110/validate-physics-first-20261111.json` (not in Git).

`scripts/build_release.py settle` ran each scene with its arms holding still until nothing
else moved and wrote that pose into the initial keyframe. The six Relay d2 and d3 scenes,
whose hanging weights pulled their timbers 4 to 9 mm in the first seconds, now start at
rest; the other scenes moved less than 0.01 mm and are unchanged.

## Step 7: Transport block letters printed upright

Each Transport block prints its letter on its top and side faces; the +y side face had the
letter's top pointing down. `scripts/build_release.py letters` turned those prints by half a
turn in the nine Transport scenes (display geoms, no contact), so runs, observation images
and videos all show them upright. `item_print_turns` in `factory/labels.py`, which turned
them in videos only, is removed.

## Step 8: one fixed code per Dial case

Each Dial run used to draw a fresh secret code. `scripts/build_release.py codes` drew one
code per Dial case, once, into the private part of `benchmark/release.json`
(`private.dial_codes`); every run of that case now uses it (`tasks.families.dial_code`), so
results of different models on the same case face the same puzzle. The code reaches only
the run's `private/inputs/suite-code.json` and the evaluator. An engineering run can still
name another code with `--private-puzzle`.

## Step 9: Relay drop recovery and scoring at rest

**Relay (T1).** A timber may be dropped, pushed or dragged. If an arm that was not holding
it when it dropped picks it up, none of its handovers counts, those before the drop
included, until the arms that held it when it fell lift it again and it is handed over again
in the air. The evaluator already detected the receiver's lift (`receiver_recovered_drop`);
it now also voids the timber's handovers, and each timber's result reports
`handovers_valid_from_s` (null while void). Continued segments carry the value. The public
rules state it (`RELAY_RECOVERY_RULE`), and the handover definition no longer says pushing
"never counts as transport".

**Finish and cutoff (T2).** Both now stop any moving arm and run the world 1.5 s with the
arms still before scoring (`RuntimeService.settled_evaluation`), so a piece set down at the
end counts once it rests: Mosaic and Transport require a piece to stay still for a second.
The cutoff records its own simulation time; the score says `scored_after_settle_sim_s`.

## Step 10: one evaluator

`tasks/evaluate_v2.py` (the released families' placement and Relay rules) is merged into
`tasks/evaluate.py`, and the branches for tasks from before the released suite are removed:
the fixed-route Relay sampler, the Mosaic and Transport goal checks of generated scenes, and
the ternary count-feedback Dial game (every released Dial case uses `tasks/dial.py`).
`Monitor.relay_v2` is now `Monitor.relay`. Tests of only those branches were removed: the

`test_dial_record_continuation`, and two Oracle contact tests on generated Transport and Mosaic
scenes in `test_suite_oracle`.

## Step 12: each case's public task, written once (T5)

A run used to build its public task at start: the reviewed projection
(`public-task.json` or `public/reviewed-task.json`) with corrections applied at run time for
terminal scoring, the Relay rules, the Mosaic target path and the family guidance. That

wrote each case's `public/task.json`, exactly the task a run received, without the run's own
protocol and image profile, and put its family materials (previews, table geometry,

| `public/task-guide.md` of the Dial cases | Nothing: the Dial skill replaced it, runs no longer received it |

## Step 13: release records

The release index now carries `release_id`, a hash of every case's files, public files,
catalogs and private codes, and `frozen`, empty until the release is frozen. Removed
because nothing reads them and the new release replaces what they recorded: the per-case
builder records (`compiled-physics.json`, `validation.json`, `static-checks.json`,
`rule-revision.json`, `transport-compatibility.json`) and the family review records
`benchmark/mosaic/{r14,selection,delivery,builder-compatibility}.json`,
`benchmark/transport/{half-opening-r14,r13-qualified,delivery}.json` and
`benchmark/dial/integration-requests.json`. The Oracle copies in `benchmark/oracle/` keep
theirs, and `benchmark/mosaic/r13.json` and `benchmark/dial/best5-r11.json` stay until the
Oracle step, which reads them.

## Step 14: finished runs keep their scores (T6)

`python -m robofrontier.analysis.rescore RUN ...` loads a finished Mosaic or Transport run's
frozen scene, puts every object where the motion recording last saw it and scores that pose
with the current evaluator. Opus's two finished Mosaic L3 runs score as recorded: a04 72 of 72,
a08 285 of 288 (`tests/analysis/test_rescore.py`, which runs where those runs are).

## Step 15: one robot tool, calls in order (E1, E2)

`robofrontier/engines/common/robot_tool.json` is the one description and schema of the
robot tool; the Claude MCP server, the Codex host and the Codex Desktop server load it, where
each had its own wording. It also says what both engines now do: calls in one reply run in
order, each after the previous one returns, and several arms move at once through one
`action_batch` or `wait:false` with `wait_events`. Claude Code already runs a reply's calls
in order. The Codex host now queues each role's calls in the order they arrive from the
pipe, which is the reply's order; before, they ran as soon as they arrived.

## Step 16: a persistent robot client for Codex (E3)

The Codex host started `python -m robofrontier.runtime.pipeline_client` for every robot call,
0.2 to 0.8 s each, 15 to 40 minutes over a run. `pipeline_client --serve` now answers
JSON-line requests until its input closes, each as the one-shot command would, and the host
keeps one such process per role (`ClientWorker` in `codex_policy_host.js`), starting a new
one if it exits. Claude's MCP server already calls the client in process.

## Step 17: pinned program versions (E4, E6)

**Owner environment (E4).** `robofrontier/engines/common/owner.py` defines the physics
process's environment for both engines: the simulation and rendering settings it needs,
never a credential, one thread for numerical libraries and two for the CPU renderer. The
Codex host used to pass its whole environment, tokens included; it now asks this module and
starts the owner in its own process group, as Claude's runner does.

**Versions (E6).** `robofrontier/runtime/versions.py` pins Claude Code 2.1.316, Codex 0.165.0,
MuJoCo 3.16.0, NumPy 2.5.4 and Pillow 12.3.0 (the lock file's versions). `robofrontier prepare`
refuses other installed versions and records the pins in `batch.json`; `robofrontier run`
checks them again, and Claude runs with `DISABLE_AUTOUPDATER=1`. The Docker image now
installs Claude Code 2.1.316 (it had 2.1.312).

## Step 18: Claude runs need receipts, not an engineering flag (E5, E13)

A Codex run already required a passed model compatibility receipt. A Claude run now needs
its passed basic and blocked precheck receipts for the same profile, CLI version and model
configuration (`engines.claude.claude_readiness.require_ready`), and the `--engineering`
flag that let an unchecked Claude batch run, with its "unqualified" wording, is removed from
`robofrontier run`, `robofrontier slurm-submit`, the Mac service and the container entry.

## Step 19: sync deadlines in simulation time, and run speed (E14, E16)

A sync group's deadline was wall time, so a group could expire during an outage pause, when
nothing could move; it is now simulation time, which stops with the world (`deadline_sim_s`).
The score written at finish and at the cutoff now carries `speed`: simulation time over
active time, the active-time stalls, and the slowest 10 minutes from the world's performance
log (`batch.metrics.simulation_speed`). It is a record for comparing hosts; a slow run is
never stopped for it.

## Step 20: model credentials stay out of the policy shell (E17)

The engine CLI that runs a policy's shell holds the model credential in its environment.
The policy environment check (`scripts/check_policy_env.py`) now also tries to read every
ancestor process's environment, through `/proc/<pid>/environ` and through `ps eww`, and
requires both to fail. On macOS both engines' sandboxes deny them (48 checks each, no
differences, 2026-11-11); Linux hosts run the same check before their first batch.

## Step 21: finish without review, and one access table (E10, E12)

**Open turns after finish (E10).** A Claude run whose team finished while a turn was still
open was marked `needs_review`; Codex only recorded it. Both now record it
(`finish_turns_drained`): the score was written at finish.

**Policy environment everywhere (E12).** `robofrontier prepare` uses a checked policy
environment on every platform: `ROBOFRONTIER_POLICY_ENV=off` and a Linux host without
`ROBOFRONTIER_POLICY_ENV_BASE`, which ran the policy on the host's Python with the whole disk
readable (access table v1), are refused. `robofrontier run` refuses any run prepared
without one. The open table stays only below the CLI, for tests that prepare runs offline.

## Step 22: long waits return as pending (E15)

A waiting move, grasp or batch could outlast Claude Code's 660 s tool-call limit when the
world ran slower than real time or paused, and Claude then saw an error while the arm kept
moving; Codex has no such limit. The robot client now returns a waiting action after 600 s
as still pending, under its original call_id (`returned_while_pending`), for both engines;
the action keeps running and `job` follows it.

## Step 23: a background service on plain Linux (PR 5)

`robofrontier run BATCH --durable` on Linux, a RunPod pod for example, now starts the batch
in the background as macOS does with launchd (`robofrontier/batch/linux.py`): a transient
systemd user service where a user manager runs, otherwise a `setsid` daemon in its own
session (RunPod containers have no systemd). The batch's control folder holds the record and
logs, a second submission is refused, and `robofrontier status` reports whether it still
runs. On Linux the access table also closes `/workspace`, a pod's volume with other runs
and data; the run's own `public/` and `workspace/` stay open below it.

## Step 24: generated Factory meshes leave Git (PR 7)

The 440 `assets/robo_factory/meshes/factory_*.obj` files are written by every Factory build
(`robofrontier.factory.scene`) and are no longer tracked (`.gitignore`); the copies on disk
stay. A second clean-up of stale meshes after the build compared the output folder with
itself and did nothing; it is removed, since the build already deletes meshes the scene no
longer uses. The textures stay tracked for now: they mix generated signs with the Poly
Haven and daylight images, and telling them apart needs a full Factory build.

## Step 25: videos show the run's own table (PR 7)

Simple-background renders and Factory workstations halved every rectangular table opening by
default, a presentation choice made when R14 halved the Transport opening physically. Videos
now show the run's own table; only a Transport recording on R13 tables is shown halved, so
it matches the released tables (`media.table_presentation.display_opening_scale`). Physics,
what agents see and videos then agree. `--table-opening-scale` still overrides it.

## Step 26: one model catalog, one effort

`configs/models.json` now holds every model profile, one section per engine
(`engines.codex`, `engines.claude`); `configs/claude-models.json` is merged into it and
`configuration.model_catalog(engine)` reads a section. A run still freezes only its engine's
section, in the same format as before. The Codex model-metadata template, which is Codex's
own format rather than a setting, moved to `robofrontier/engines/codex/model_template.json`.
Every profile on both engines uses `effort: high` (Qwen and GLM under Codex used `xhigh` and
`max`).

## Step 27: Oracle source scenes, and no more earlier scene revisions (PR 6)

`configs/environments/` (1,944 tracked files, every scene revision the builder made) and
`configs/suites/` (their catalogs and preview images) are removed. The Oracle keeps what it
was developed and recorded on, in `benchmark/oracle/`: the copy of each released case (step 5)
and, under `benchmark/oracle/sources/`, the Transport r13, Mosaic r13 and Relay r16 scenes with
the Transport r13 catalog. `benchmark/legacy-paths.json` maps their earlier paths there. The
untracked asset files of the removed revisions (1.6 GB on this Mac) were moved to
`~/.Trash/robofrontier-cleanup-20261110/configs-environments-untracked-20261111`.

Tests of only the removed revisions were removed: `tests/oracle/test_dial_oracle_v2.py` (r10),

## Step 28: one stop table, usage-limit pauses, one capacity text (PR 5, E7–E9)

**E7.** `runtime/segments.py` has one stop table (`STOP_REASONS`): why the current segment
ended (`stop_reason`: unexpected, finish, cutoff, wall backstop, operator stop, integrity
abort) decides what may follow. An unexpected stop continues by itself once per run; a live
seal after a model-side failure now counts as unexpected (it was a normal end). Any stop but
an integrity abort may be continued by hand with the new `robofrontier continue BATCH
[--cases …]`, as often as needed; it reopens the batch for those runs only. A continuation
after the finish or the cutoff is marked `after_score`: `scored-evaluation.json` and
`scored-budget-cutoff.json` keep the score, and the budget guard and the Claude supervisor set
no limit or backstop for it. The Claude batch now asks the table after every supervisor end
but its own limit, a STOP, a finished run or a launch failure, as the Codex batch does.
`MAX_RETRIES` and the `sealed_host_failure` exception are gone; the task-recovery entries
continue by hand.

**E8.** A turn that fails on the plan's usage limit (`runtime/quota.py` reads Claude Code's
and Codex's texts and the reset time) asks the world to pause (`runtime_cli quota-pause`).
The world holds itself as in an outage until a minute after the reset (30 minutes when no time
is readable), then each such role continues once with the frozen `quota-resume.md`; the
operator gets a line in `notifications.jsonl` and a macOS notification. Outage, egress and
usage-limit pauses no longer count toward the 48 h wall backstop (`clock.backstop_elapsed`).
The outage probe asks the host of the profile's `base_url` and also runs on Slurm jobs with
direct egress; the Slurm `mac-ssh` pause may last up to the backstop and does by default
(`slurm.egress_pause_s = 172800`; the 600 s cap is gone).

**E9.** Both hosts send the same frozen `capacity-resume.md` after a capacity retry
(`bootstrap.MAX_CAPACITY_RETRIES = 3`), and both pause dispatch when the retries are used up
(the Claude host used to fail the session instead).

Not verified with a real model: the exact texts the CLIs print at a usage limit come from
their documentation and the 2026-11-10 stop; the parser falls back to a 30-minute recheck when
it cannot read one.
